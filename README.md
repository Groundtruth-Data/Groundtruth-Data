# Groundtruth Data

**Evidence-backed evaluations for AI factual reliability.**

Groundtruth Data helps AI teams measure where models get facts wrong, inspect the evidence behind each failure, and build targeted data for follow-up work. We create evaluation datasets grounded in authoritative records—not answer keys generated by another language model.

The workflow is deliberately separated into three stages:

1. **Prove the baseline.** Evaluate a defined capability against source-backed reference answers and explicit grading rules.
2. **Target the failures.** Build remediation examples around reviewed, demonstrated weaknesses.
3. **Validate separately.** Measure a later system run on cases kept outside remediation and training.

Groundtruth provides evaluation and data. It does **not** automatically train or modify a customer's model, and creating remediation data is not itself proof of model improvement.

## What Groundtruth delivers

| Deliverable | Purpose |
| --- | --- |
| Proof evaluation | Measure a defined capability using answerable questions, verified references, provenance, and grading rules. |
| Failure analysis | Preserve model outputs and categorize observed errors so teams can understand what failed. |
| Remediation dataset | Provide reviewed corrections and examples targeted at demonstrated failure modes. |
| Held-out validation set | Keep separate cases for measuring a later run without reusing remediation examples. |
| Custom failure study | Scope a new evaluation around a team's task, sources, and requirements. |

Packages differ in source coverage, case count, included artifacts, and publication status. See the status notes below; do not assume every listed asset is available for immediate purchase.

**Source:** OpenAlex

- **869 / 1,000 correct (86.9%)**
- **131 / 1,000 incorrect (13.1%)**

## Try the public benchmark sample

A 180-row sample is available on Hugging Face:

[Groundtruth Data Hallucination Benchmark Sample](https://huggingface.co/datasets/Groundtruth-Data/groundtruth-hallucination-bench-sample)

The sample spans research citations, clinical trials, FDA safety data, code execution and package behavior, Companies House records, SEC filings, legal facts, math, science, history, geography, government data, and cross-source verification.

### Quick start

1. Download or load the public sample from Hugging Face.
2. Give the model only the `question` field. Do not include `verified_answer`, `verification_summary`, source URLs, or prior model responses in the model's prompt.
3. Save the exact model response together with the model name, model version, run date, and whether retrieval was enabled.
4. Compare the response with the reference answer and provenance. Review apparent mismatches for synonyms, scope, and source timing before assigning a failure.

The public sample is intended for schema inspection and quick diagnostics. It is **not** an untouched held-out set and must not be used to claim post-training improvement.

### Sample fields

Rows include:

- `id`, `dataset`, and `domain`
- `question` and `verified_answer`
- `verification_summary` and `source_urls`
- `reference_model` and `model_response`
- `verdict`, `grading_mode`, `difficulty`, and `tags`

The repository's `samples/` directory contains a quick-start guide; the full 180-row public sample is hosted on Hugging Face rather than duplicated here.

## How verification works

Groundtruth does not treat another model's output as factual ground truth. Depending on the task, reference evidence can come from:

- authoritative APIs and government databases
- official filings and registries
- primary-source documents
- structured publication metadata
- package source archives
- direct Python or Node execution
- deterministic computation

A typical evaluation follows this process:

```text
authoritative source
       |
       v
verified source record
       |
       v
answer-free evaluation question
       |
       v
model response
       |
       v
source-aware or deterministic grading
       |
       v
reviewed failure analysis
       |
       v
targeted remediation (when justified)
       |
       v
separate held-out validation
```

### Separation matters

- **Proof cases** measure the starting point.
- **Remediation cases** are used to develop or target an intervention.
- **Held-out cases** must remain outside remediation and training if they are to provide an independent validation measurement.

A split label alone does not establish independence. Overlap, source versions, task scope, grading rules, and any use of validation results during tuning should be reviewed and disclosed.

### Interpreting results responsibly

A benchmark result applies to the exact dataset, source truth, model and interface, run date, and grading method used. It should not be generalized into a universal model score or broad capability claim. A source timeout or unavailable record is not automatically a model error; ambiguous matches require review.
